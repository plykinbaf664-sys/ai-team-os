AI Team OS - обновление 25.07.2026

Внутренняя Telegram-first система управления личным AI-ассистентом и AI-командой для клиентских проектов.

Проект создаётся как отдельный репозиторий и не является коммерческим SaaS-продуктом или шаблоном для продажи. Его задача — закрывать личную операционную работу пользователя и координировать производство результатов по клиентским проектам через специализированных AI-агентов.

1. Главная идея

В Telegram используется один физический бот, внутри которого работают разные независимые роли.

Два верхнеуровневых агента:

Assistant Agent — личный ассистент пользователя.

Project Agent — руководитель AI-команды по клиентским проектам.

Они не вызывают друг друга, не передают друг другу задачи и не ведут автоматический диалог между собой.

Пользователь сам выбирает, к кому обратиться:

/assistant — личная и операционная работа
/project   — комплексная работа по клиентскому проекту

2. Архитектура агентов

Пользователь
├── Assistant Agent
│   └── личные дела и внутренние проекты пользователя
│
└── Project Agent
    └── клиентские проекты и управление AI-командой
        ├── Research Agent
        ├── Product Agent
        ├── Funnel Agent
        ├── Content Agent
        ├── Scraper Agent
        ├── Social Copywriter
        └── Reels Scriptwriter

Ключевое ограничение

Assistant Agent ≠ Project Agent

Assistant Agent не управляет специализированными агентами.

Project Agent не занимается личной операционкой пользователя.

Assistant Agent не вызывает Project Agent.

Project Agent не вызывает Assistant Agent.

Специализированные агенты не вызывают друг друга.

Только Project Agent может запускать специализированных агентов.

Он работает с личными делами, операционной нагрузкой и собственными внутренними проектами пользователя.

LLM используется только для:

9. Защита от зацикливания

Обязательные правила:

корневой workflow запускает только пользователь;

Assistant Agent и Project Agent не вызывают друг друга;

специализированные агенты вызываются только Project Agent;

специализированный агент не запускает другого агента;

ответ бота не считается новым пользовательским запросом;

каждый workflow имеет trace_id;

дочерний запуск имеет parent_run_id;

одинаковый агент с одинаковым payload не запускается повторно внутри одного trace;

в MVP max_agent_depth = 1;

после финального результата workflow закрывается;

свободное bot-to-bot общение запрещено.

10. Безопасность

Подтверждение обязательно перед:

удалением данных;

удалением задач;

удалением событий;

массовым обновлением;

очисткой таблиц;

перезаписью большого диапазона;

необратимыми действиями.

обновление одного статуса;

получение аналитической сводки.

17. Критерий успеха MVP

Первая рабочая версия считается готовой, когда:

В Telegram существуют два независимых входа: Assistant Agent и Project Agent.

Assistant Agent понимает текстовое или голосовое поручение.

Assistant Agent создаёт типизированный набор действий.

Assistant Agent безопасно обновляет Google Sheets, TickTick и Calendar.

Assistant Agent считает показатели обычным кодом.

Project Agent создаёт план клиентского проекта.

Project Agent последовательно вызывает специализированных агентов.

Агенты не зацикливаются и не разговаривают бесконечно.

Все действия логируются.

Пользователь получает короткий понятный результат в Telegram.

2. Архитектура агентов

В системе существуют два независимых верхнеуровневых агента:

Assistant Agent

Project Agent

Они не вызывают друг друга, не передают друг другу задачи и не ведут автоматический диалог между собой.

Пользователь сам выбирает нужного агента.

Пользователь
├── Assistant Agent
│   └── личные дела и внутренние проекты пользователя
│
└── Project Agent
    └── клиентские проекты и управление AI-командой
        ├── Research Agent
        ├── Product Agent
        ├── Funnel Agent
        ├── Content Agent
        ├── Scraper Agent
        ├── Social Copywriter
        └── Reels Scriptwriter

Ключевое ограничение

Assistant Agent ≠ Project Agent

Assistant Agent не вызывает Project Agent.

Project Agent не вызывает Assistant Agent.

Assistant Agent не управляет специализированными агентами.

Project Agent не занимается личной операционной работой пользователя.

Специализированные агенты не вызывают друг друга.

Только Project Agent может запускать специализированных агентов.

Канонический slug:

assistant

Он отвечает за личные дела, собственные проекты пользователя, задачи, показатели, таблицы, дедлайны, встречи и ежедневную операционную работу.

проверять результат;

8. TickTick

Assistant Agent подключён к TickTick и умеет работать с задачами.

Поддерживаемые действия

создать задачу;

обновить задачу;

завершить задачу;

назначить дедлайн;

изменить дедлайн;

назначить приоритет;

выбрать список или проект;

изменить статус;

найти существующую задачу;

проверить возможный дубль;

вернуть ссылку или ID созданной задачи.

Главное правило

В TickTick создаются только конкретные задачи, которые ведут к определённому результату.

Нормальные задачи:

Подготовить презентацию к пятнице
Согласовать оффер с Мариной
Проверить лендинг до 30 июля

Массовые процессовые действия не дробятся на десятки задач:

Написать 90 людям
Обработать всю базу
Каждый день отвечать на комментарии

Такие действия должны фиксироваться как KPI, процесс или чек-лист внутри одной задачи, если это действительно необходимо.

11. Следующая стадия: Sheets ↔ TickTick Coordination Layer

Цель

Связать Google Sheets и TickTick так, чтобы Assistant Agent управлял ими как одной системой, но не смешивал разные типы данных.

Главный принцип

Google Sheets = данные, реестры, показатели, статусы и аналитика

TickTick = конкретные задачи, дедлайны, приоритеты и выполнение

Assistant Agent должен определять

Только Google Sheets

факт отправок;

показатели;

расходы;

выручка;

лиды;

продажи;

статусы контактов;

аналитические данные;

реестры;

история гипотез;

план-факт.

Только TickTick

конкретное действие;

ответственный шаг;

дедлайн;

напоминание;

приоритет;

завершение задачи.

Google Sheets и TickTick одновременно

Действие затрагивает обе системы только тогда, когда существует реальная связь между учётной сущностью и конкретной задачей.

Пример:

Добавь Марину в таблицу партнёров со статусом «Созвон назначен»
и создай задачу подготовить предложение к 13 августа.

Результат:

В Google Sheets обновляется строка Марины.

В TickTick создаётся одна задача.

Между строкой и задачей сохраняется связь.

Пользователь получает единый отчёт.

13. Source of Truth

Чтобы не получить хаос, у каждого типа данных должен быть основной источник.

Google Sheets — источник истины для

показателей;

реестров;

контактов;

статусов лидов;

аналитики;

план-факта;

результатов;

истории гипотез.

TickTick — источник истины для

статуса выполнения задачи;

дедлайна задачи;

приоритета;

даты завершения;

списка задач;

конкретного следующего действия.

Правило синхронизации

Если задача завершена в TickTick, Assistant Agent может обновить связанный статус в Google Sheets только по заранее определённому mapping rule.

Пример:

TickTick task completed
→ linked sheet row
→ поле «Следующее действие» очищается
→ поле «Статус задачи» меняется на «Выполнено»

Нельзя автоматически менять бизнес-статус лида только потому, что была закрыта техническая задача.

Например:

Задача «Подготовить КП» выполнена

не означает автоматически:

Сделка закрыта

14. Coordination Rules

Правило 1. Не создавать дубли

Перед созданием задачи проверять:

нормализованный заголовок;

проект;

дедлайн;

связанную сущность;

существующий TickTick task ID;

idempotency key.

Правило 2. Не создавать задачу из любого статуса

Статус в таблице не всегда является задачей.

Пример:

Статус: ожидает ответа

не должен автоматически создавать задачу без дополнительного правила.

Правило 3. Не дробить массовые действия

Написать 90 людям

может быть:

одной задачей;

KPI в таблице;

одной задачей с чек-листом;

плановым показателем.

Но не 90 отдельными задачами.

Правило 4. Обновлять только связанные сущности

Assistant Agent не должен искать похожую строку и менять её без уверенного совпадения.

При нескольких совпадениях он задаёт один уточняющий вопрос.

Правило 5. Частичный успех должен быть виден

Если таблица обновилась, но TickTick вернул ошибку:

Google Sheets: выполнено
TickTick: ошибка

Нельзя отвечать пользователю, что вся операция выполнена успешно.

Правило 6. Все изменения логируются

Для каждой операции хранить:

входное сообщение;

action plan;

исполнителя;

целевую систему;

payload без секретов;

результат;

ошибку;

timestamp;

idempotency key.

17. Acceptance Criteria следующей стадии

Стадия считается завершённой, когда:

Assistant Agent правильно различает данные и задачи.

Метрики не превращаются в задачи.

Задачи без необходимости не записываются в таблицу.

Связанные действия выполняются в обеих системах.

Между строкой таблицы и задачей сохраняется стабильная связь.

Повтор одного сообщения не создаёт дубль.

Ошибка одной системы не скрывает успех другой.

Выполнение задачи обновляет только разрешённые поля таблицы.

Все операции фиксируются в audit log.

Пользователь получает короткий единый отчёт.

Все TypeScript, lint, test и build проверки проходят.

Есть ручные тесты на реальные Google Sheets и TickTick.

18. Безопасность

Подтверждение обязательно перед:

удалением строк;

удалением задач;

массовым обновлением;

массовой синхронизацией;

изменением структуры таблицы;

переносом большого количества задач;

перезаписью диапазона;

автоматическим исправлением конфликтов между системами.

Не требуют подтверждения:

создание одной явно указанной задачи;

показать план;

перечислить изменяемые файлы;

реализовать только текущий scope;

запустить TypeScript;

запустить lint;

запустить тесты;

запустить build;

показать ручную проверку;

Codex не должен:

деплоить;

менять webhook;

показывать секреты;
